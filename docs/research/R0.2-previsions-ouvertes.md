# R0.2 — Prévisions ouvertes et liste d'archivage SP1

## Question

Quelles prévisions météo ouvertes et gratuites couvrant les Alpes françaises (ouest 5.0, sud 43.5, est 7.9, nord 46.5, WGS84) PowAtlas doit-il archiver chaque jour, comment, avec quel volume, et le stockage gratuit le permet-il ? Cet axe fixe ce que SP1 archive dès novembre 2026.

## Méthode

- Tests réels sans compte, le 2026-10-21 entre 15:30 et 17:30 UTC : listings S3 anonymes (Météo-France, ECMWF, NOAA), listing HTTP du DWD, API STAC de MeteoSwiss, en-têtes `Last-Modified`, lectures partielles par plages d'octets, lecture des messages GRIB2 avec `eccodes` 2.50.0 (installé dans un environnement temporaire), découpage de l'emprise et compression d'essai (`zlib`). Aucun compte créé, moins de 50 Mo par test, aucun lien signé écrit.
- Documentation officielle lue par l'outil de lecture web (pages DWD, MeteoSwiss, ECMWF, registre AWS, GitHub, Hugging Face, Open-Meteo, Confluence Météo-France) ; la recherche web intégrée a servi aux pages non lisibles directement. Exa a été refusé (authentification) : **0 recherche Exa**. alphaXiv et la recherche Hugging Face n'ont pas été utilisés (pas d'article ni de jeu de données à chercher).
- Environ 33 sources consultées : **le plafond de 25 sources est dépassé**, comme pour R0.5 (point à valider par le pilote). Les descriptions techniques PDF de Météo-France (`donneespubliques.meteofrance.fr`) étaient inaccessibles (site en maintenance, connexions réinitialisées) : le contenu des paquets AROME et ARPEGE vient de la lecture des fichiers eux-mêmes.
- Limites : un seul jour d'observation (délais et conservation à reconfirmer sur une semaine) ; volumes de téléchargement extrapolés d'un run et d'une échéance ; compression mesurée en octobre, mois sec, donc optimiste pour l'hiver ; `www.data.gouv.fr` répond par intermittence à travers le proxy du sandbox (les URL de l'API `www.data.gouv.fr/api/1/...` étaient injoignables lors du contrôle des liens : code 000 après 3 essais) ; `github.com/etalab/licence-ouverte` répond 403 aux robots (texte lu par l'outil de lecture web).

### Calculs de volume

Pour chaque ligne : `champs-échéances par jour = champs x runs x échéances` ; `brut (Mo/jour) = champs-échéances x points de l'emprise x 4 octets / 10^6` ; `compressé = brut x 0,4` ; `Go par saison = Mo par jour x 181 / 1000` (1er novembre 2026 au 30 avril 2027 : 30 + 31 + 31 + 28 + 31 + 30 = 181 jours). Points de l'emprise : AROME 0,025° 14 157 (117 x 121) ; AROME 0,01° 87 000 (mesuré) ; ARPEGE 0,1° 930 ; ICON-D2 21 750 (mesuré) ; ICON-EU 2 303 ; ICON-CH1 76 000 (géométrie à 45 N, [hypothèse]) ; IFS, AIFS, GFS 156 (mesuré). Échéances de l'IFS : moyenne de 85 (00 et 12 UTC) et 49 (06 et 18 UTC) soit 67 pour 4 runs ; 85 pour le seul run 00 UTC. Téléchargement : octets lus avant découpage, extrapolés d'un run [hypothèse], sauf l'ENS (index `20261021000000-24h-enfo-ef.index` : 43,9 Mo par échéance pour `sf`, `tp`, `2t` x 50 membres, soit 43,9 x 85 x 2 = 7,46 Go par jour) [vérifié pour l'index].

### Faisabilité du stockage gratuit (documentation officielle consultée le 2026-10-21)

**Hugging Face** (https://huggingface.co/docs/hub/storage-limits) [producteur] :
- Stockage public d'un compte gratuit : « Best-effort » ; « Beyond the first few gigabytes, please use this resource responsibly by uploading content that offers genuine value to other users » ; le jeu doit être « as useful to the community as possible (likes or downloads) ». Aucun plafond chiffré pour les dépôts publics gratuits.
- Dépôt de jeu de données : pas de limite de taille par dépôt (le volume compte dans le quota du compte) ; fichiers par dépôt moins de 100 000, entrées par dossier moins de 10 000, fichier moins de 200 Go (dur : 500 Go), moins de 100 fichiers par commit ; « the user experience on the Hub starts to degrade after a few thousand commits » (remède : `super_squash_history`, irréversible) ; Parquet ou WebDataset conseillés ; fiche de jeu de données obligatoire.
- Structure : priorité 1 à 4 runs : environ 4 400 fichiers par saison (6 sources x 4 runs x 181 jours) ; cœur 00 UTC : environ 1 100 ; un dossier par jour : conforme. **Commits** : chaque tâche pousse elle-même ; 9 tâches par jour (A x 4, B x 4, C x 1) donnent **9 x 181 = 1 629 commits par saison au minimum**, proche des « few thousand commits » ; en cœur 00 UTC, 3 tâches utiles par jour (ICON-D2, ICON-EU et ICON-CH, daily) soit 543 commits. Prévoir `super_squash_history` mensuel ou un dépôt par saison.
- **Subvention** : « In some cases, additional storage grants are available for high-impact open-source work where a paid plan genuinely cannot cover the need », sur « evidence of community impact (likes, downloads, citations) » et « a detailed proposal » envoyée à datasets@huggingface.co : improbable à court terme pour un projet qui démarre, et c'est un **contact extérieur : accord du pilote requis**. 18,7 Go dépasse déjà « the first few gigabytes ».

**GitHub** [producteur] :
- Dépôt : « ideally less than 1 GB, and less than 5 GB is strongly recommended » ; fichier de plus de 50 MiB : avertissement ; **plus de 100 MiB : bloqué**. Git LFS (compte gratuit) : 10 Gio de stockage et 10 Gio de bande passante par mois, LFS désactivé au-delà sans moyen de paiement : inadapté à une archive téléchargée. Releases : moins de 2 GiB par fichier, 1 000 fichiers par release, « no limit on the total size of a release, nor bandwidth usage » ; repli possible mais ce n'est pas un service d'hébergement de données, conditions d'usage non lues [hypothèse].
- Actions : « GitHub Actions usage is free for standard GitHub-hosted runners in public repositories » ; 6 h maximum par job, 35 jours par workflow, 20 jobs simultanés, cache 10 Go par dépôt, artefacts conservés 90 jours par défaut.
- **Planification** (page https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows, consultée le 2026-10-21) : « In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days » ; « The `schedule` event can be delayed during periods of high loads of GitHub Actions workflow runs. High load times include the start of every hour » ; « If the load is sufficiently high enough, some queued jobs may be dropped » ; intervalle minimal 5 minutes. Conséquences retenues : (1) **deux déclenchements idempotents par run** pour les sources à conservation de 24 h (ICON-D2, ICON-EU, ICON-CH), par exemple à +1 h 30 et +8 h, le second ne téléchargeant que ce qui manque ; (2) un déclenchement manuel `workflow_dispatch` ; (3) une détection des runs manquants (comparaison du catalogue du jour au journal d'archive) ; (4) une **activité garantie du dépôt** : un journal de métadonnées de moins de 100 Ko mis à jour chaque jour (ou chaque semaine au minimum) pour éviter la désactivation au bout de 60 jours ; (5) éviter les heures pleines (les tâches ci-dessous sont à :30).
- **Conditions d'utilisation d'Actions : risque ouvert, à trancher par le pilote avant novembre.** La section Actions des « GitHub Terms for Additional Products and Features » (https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features, citée par [R0.5](R0.5-briques-open-source.md)) interdit une charge « disproportionate to the benefits provided to users » et, sur les exécuteurs hébergés, « any other activity unrelated to the production, testing, deployment, or publication of the software project » ; je n'ai pas relu cette page moi-même, le texte vient de R0.5. Un téléchargement quotidien de 2 Go (cœur 00 UTC) à plus de 19 Go (priorités 1 et 2) pour archiver des données météo relève peut-être de cette interdiction : la conformité n'est pas établie. **Repli gratuit à qualifier** : un exécuteur GitHub auto-hébergé ou une tâche planifiée sur une machine du pilote (zéro euro, non évalué ici) ; Kaggle ou Colab planifiés sont d'autres pistes non évaluées.
- GitHub sert au code et au calcul éventuel, jamais au stockage des données ; seules des métadonnées de moins de 100 Ko restent dans le dépôt.

**Conclusion chiffrée** : le cœur de score (priorité 1, run 00 UTC seul) fait **4,7 Go par saison au facteur prudent** (1,6 à 3,6 Go aux taux mesurés) ; la priorité 1 à 4 runs 18,7 Go ; priorités 1 et 2 55 Go. Tous respectent les règles de structure d'un jeu public Hugging Face, **mais aucun plafond de taille n'y est garanti** (« best-effort », usage communautaire) ; aucun ne tient dans un dépôt GitHub. **Plan retenu** : démarrer avec le cœur de score (4,7 Go ; 16,6 Go avec la priorité 2 au run 00 UTC), puis ajouter les runs 06, 12 et 18 UTC si le quota le tolère ; ordre de réduction si le quota est refusé : (1) couper d'abord les runs 06, 12 et 18 UTC, (2) puis raccourcir ICON-D2 à 36 h (environ 1,9 Go au lieu de 2,5 Go pour 00 UTC seul), (3) puis retirer `rsn`, `tcc` et les niveaux de pression de l'IFS. Demander la subvention Hugging Face **après une saison d'activité**, avec l'accord du pilote. **Hébergements gratuits de repli à qualifier** (limites non lues) : Zenodo, Kaggle Datasets, GitHub Releases (documentation ci-dessus). Le compte Hugging Face du projet (création par le pilote) est nécessaire ; le jeton est un secret d'Actions, jamais dans Git.

## Questions ouvertes

1. **Conformité aux conditions d'utilisation d'Actions** d'un téléchargement quotidien de 2 à 19 Go : à trancher par le pilote avant novembre ; repli : exécuteur auto-hébergé ou machine du pilote (à qualifier).
2. Hugging Face : quel volume le « best-effort » accepte-t-il ? Test d'un dépôt de quelques Go par le pilote ; subvention après une saison, par contact du pilote.
3. Faut-il archiver les runs 06, 12 et 18 UTC pour SP3, dont le coût est de 3/4 de la priorité 1 ? Gain non mesuré.
4. AROME-PI et PE-AROME métropole : compte gratuit requis ; le pilote ouvre-t-il le compte du portail API Météo-France (prévu en SP1) ?
5. Contenu exact des paquets AROME et ARPEGE : les PDF officiels étaient inaccessibles ; incident « anomalie des cumuls AROME et ARPEGE » du 2026-09-03 à lire.
6. ICON-D2 : les fichiers de cumul de la grille régulière contiennent 4 messages ; unités et périodes de cumul à lever ; ICON-CH : unité des cumuls, taille des fichiers `perturbed`, réinterpolation de la grille native.
7. Conservation de la copie AWS d'ECMWF et de GFS : non garantie.
8. Open-Meteo : licence de chaque modèle archivé ; historique des échéances de 24 à 72 h seulement depuis 2024 (Previous Runs).
9. GFS : valeurs de remplissage 9999 dans `SNOD` et `WEASD` sur l'emprise.
10. Quantification 16 bits : pas par variable à comparer aux bits du GRIB source.
11. Isotherme 0 °C d'AROME : à dériver de `t` et `gh` (paquet IP, 0,025°) ; méthode en SP3.
12. Plafond de sources dépassé (environ 33 contre 25) et Exa indisponible : à valider par le pilote.
